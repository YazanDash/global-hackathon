You are creating a new Python project called BudgetDev from scratch in this empty directory.

BudgetDev is a token-efficient coding agent for an AI hackathon. Its problem statement is:
"Build a coding agent that gets the job done with the fewest tokens."

Important distinction:
- This repository is the BudgetDev agent project.
- The coding agent built by this project will later operate on a separate target workspace passed through --workspace.
- It must not modify BudgetDev's own source files during normal operation.
- File tools must resolve paths relative to the target workspace and reject path traversal.

Your task:
1. Initialize this folder as a Git repository.
2. Create README.md documenting the project vision, architecture, milestones, and usage.
3. Implement ONLY Milestone 1 now.
4. Do not implement the Repo Atlas, semantic search, embeddings, model routing, dashboard, or incremental re-indexing yet.

## Product vision for README.md

BudgetDev will eventually:
- Receive a bug report or feature request.
- Plan before reading code.
- Search a prebuilt semantic index of the repository, called the Repo Atlas.
- Read only the smallest relevant code windows.
- Apply minimal patches.
- Run targeted tests.
- Track every token spent.
- Route cheap work to a cheap model and difficult coding work to a stronger model through Bifrost.

For Milestone 1, build only the baseline agent. This baseline is important because later milestones must prove that the Repo Atlas and budget controller reduce token usage compared with it.

## File tools

In budgetdev/tools/files.py, implement:

1. list_files(root=".")
- List relative file paths.
- Ignore .git, __pycache__, .venv, venv, node_modules, .pytest_cache, and compiled Python files.
- Limit output to 200 files.

2. grep(pattern, root=".")
- Search text files recursively.
- Return matches as path:line: matching line.
- Limit to 50 matches.

3. read_file(path)
- Read a UTF-8 text file.
- If it has more than 400 lines, return only the first 400 lines and tell the agent to use read_lines.

4. read_lines(path, start, end)
- Return the requested 1-based inclusive line range.
- Include at most 10 lines of context before and after.
- Format output as:
  path:start-end
  42: def example():
  43:     ...

5. write_patch(diff)
- Accept a unified diff.
- Apply it safely to the target workspace.
- Prefer `git apply --whitespace=nowarn` through subprocess when the workspace is a Git repository.
- If Git is unavailable, implement a minimal safe fallback for simple unified diffs.
- Reject diffs that write outside the workspace.
- Never use eval, exec, or unsafe shell interpolation.

Security rules:
- All paths must resolve inside the target workspace.
- Reject ../ traversal and absolute paths outside the workspace.
- Handle symlinks safely.

## Agent

In budgetdev/agent.py:
- Create CodingAgent.
- Constructor takes client, registry, ledger, and settings.
- Implement:

def run(self, issue, max_tokens=None) -> AgentResult

- AgentResult must include success, final_message, patch, total_tokens, steps_used, and stopped_reason.
- Implement a ReAct-style loop:
  1. Send the system prompt and issue to the model.
  2. If the model returns a tool call, execute it.
  3. Log the LLM call and tool execution.
  4. Compress the tool result.
  5. Append the result to the conversation.
  6. Repeat.
  7. If the model calls finish, return the final patch and explanation.
  8. Stop after max_steps or when the token budget is exceeded.

Use this system prompt:

You are BudgetDev, a token-efficient coding agent.

Your goal is to resolve the user's software issue with the fewest tokens possible while producing a correct, test-passing change.

Rules:
1. Think before acting, but keep your reasoning short.
2. Use list_files or grep only when necessary.
3. Prefer read_lines over read_file.
4. Read only the smallest relevant code range.
5. Make the smallest change that correctly resolves the issue.
6. Run only relevant tests when possible.
7. If tests fail, read the compressed failure output and make one focused correction.
8. Do not rewrite entire files.
9. Do not add unrelated features, comments, refactors, or documentation.
10. When the change is complete and tests pass, call finish.

Available tools:
- list_files
- grep
- read_file
- read_lines
- write_patch
- run_tests
- finish

The finish tool accepts:
- explanation: short explanation of the change
- patch: final unified diff

finish must not perform any side effect.
